# TimingEvent Entity Specification

## 1. Purpose
A **TimingEvent** represents a single atomic timing signal generated by a camera or timing device. These events are the raw inputs used to determine start times, finish times, splits, and other timing‑related metrics for a Run. TimingEvents are immutable records that reflect exactly what the hardware observed.

---

## 2. Definition
A TimingEvent is a timestamped detection emitted by a camera or timing device. It may represent:
- a **start** trigger  
- a **finish** trigger  
- an **intermediate split**  
- a **false trigger** or noise event (filtered during validation)

TimingEvents are always stored exactly as received, without modification.

---

## 3. Attributes

### Core Fields
- **id** — Unique identifier for the timing event  
- **event_id** — Reference to the Event  
- **camera_id** — Reference to the Camera that generated the event  
- **run_id** — Optional reference to the Run this event is associated with  
- **type** — One of: `start`, `finish`, `split`, `unknown`  
- **timestamp** — High‑precision timestamp from the timing device  

### Metadata
- **sequence_number** — Monotonic counter from the camera (if supported)  
- **raw_payload** — Original unparsed data from the device  
- **confidence** — Optional confidence score (for OCR‑based systems)  
- **created_at** — Timestamp when the event was recorded in the system  

---

## 4. Relationships

### Parent
- **Event** — All timing events belong to an event  
- **Camera** — All timing events originate from a specific camera  

### Optional Parent
- **Run** — TimingEvents may be associated with a run after validation or manual assignment  

### Children
None — TimingEvents are leaf‑level atomic records.

---

## 5. CameraSessions and Role Attribution

TimingEvents always reference the **physical camera** (`camera_id`) that generated the event.  
The active **CameraSession** determines the timing role (start, finish, split) at the moment the event occurred.

This allows:
- seamless camera replacement  
- accurate interpretation of TimingEvents  
- preservation of historical hardware data  

Validation uses the CameraSession timeline to determine how each TimingEvent should be interpreted.

---

## 6. Event Flow & Association Logic

TimingEvents follow this general flow:

```
Camera → TimingEvent → (optional) Run association → Validation → Results
```

### Association Rules
- A TimingEvent may initially have **no run_id**.  
- Association may occur via:
  - automated matching (based on staging order and timestamps)  
  - manual assignment by a worker  
  - validation pipeline inference  

### Start/Finish Logic
- A **start** TimingEvent may move a Run from `CREATED` → `IN_PROGRESS`.  
- A **finish** TimingEvent may move a Run from `IN_PROGRESS` → `FINISHED`.  
- Multiple TimingEvents may be associated with a single run; validation determines which are authoritative.

---

## 7. Constraints & Invariants

- TimingEvents are **immutable** — once stored, they cannot be edited or deleted.  
- A TimingEvent must always reference a **camera_id**.  
- A TimingEvent may exist without a **run_id** indefinitely.  
- A TimingEvent’s `timestamp` must be monotonic per camera (if supported by hardware).  
- A TimingEvent’s `type` may be `unknown` until validation resolves it.  
- A TimingEvent may be associated with at most one run.  

---

## 8. Notes & Implementation Guidance

- Always store the **raw payload** for auditability and debugging.  
- Do not infer meaning (start/finish) at ingestion time — classification belongs to validation.  
- Cameras should ideally provide sequence numbers to detect dropped or duplicated frames.  
- The system should tolerate:
  - out‑of‑order events  
  - duplicate events  
  - noisy or false triggers  
- Validation should be idempotent and able to re‑evaluate TimingEvents without creating duplicates.  
- Manual reassignment of TimingEvents should be logged for traceability.
